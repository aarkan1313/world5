# W5 Re-Audit — Phases 0-5 spec compliance

> Date: 2026-05-17
> Trigger: Walking demo's Phase 5.4 alpine first-biome render exposed
> two unspec'd-but-shipped gaps (multi-page heightmap binding +
> per-fragment slot selection). User direction: re-audit the whole
> project rather than patching symptoms — "even if this means we are
> starting from Phase 0 again."

## Purpose

For each phase that ROADMAP marks ✅ done, compare what each owning
spec **requires** against what the codebase **actually ships**.
Output a punch-list of every gap with severity + estimated effort.

The roadmap can then either (a) re-open the affected phases until
their specs are satisfied, or (b) explicitly amend the affected specs
to match shipped scope. Either way the roadmap stops being out of
sync with reality.

## Method

For each spec:

1. Read the spec's "Public API" + "Quality bar" + "Discoverability"
   sections — the contract the spec claims to deliver.
2. Read the corresponding code under `engine/scripts/`, `pipeline/`,
   or `engine/shaders/`.
3. Identify gaps:
   - **Missing**: spec requires X, code has nothing
   - **Partial**: spec requires X with N properties; code has it but
     missing some properties
   - **Wrong**: spec requires X; code has Y that conflicts
   - **Untested**: spec requires X; code has it but no test asserts
     it works
4. Tag each gap with:
   - **Severity**: critical (visible-to-user / spec-blocker),
     significant (correctness issue, not visible), minor (polish)
   - **Effort**: 1 session / 2-3 / 4+ / multi-sprint
   - **Spec reference**: exact spec section
   - **Code reference**: file:line

## Output

A punch-list at `docs/AUDIT_FINDINGS_PHASE_0_5_2026_05_17.md` ranked
by severity. Each entry self-contained: gap description + spec quote
+ code reference + recommended fix sketch.

## Known visible-user findings (seed evidence — these MUST appear
in the punch-list or the audit missed them)

1. **Outer clipmap rings sample one page → chunk seams visible**
   - Spec: 21_TERRAIN_RENDERER (no explicit "no seam" but implicit
     in "60fps zero hitches + full detail")
   - Code: `engine/scripts/terrain/TerrainWorld.gd:444-452` binds
     single page per ring; ring extents > page extent for rings 2-4
   - Severity: critical (user-visible bug)

2. **Per-fragment slot selection not implemented → mid/rock textures
   never render**
   - Spec: 23_MATERIALS_PBR §"Surface slot model" — "Surface slot
     world mask bakes these into a shared Texture2DArrayRD sampled
     at world XZ"; 22_BIOME_CATALOG declares per-slot selectors
   - Code: `engine/scripts/terrain/material/SurfaceSlotMask.gd` only
     loads JSON metadata; no shader code does selection;
     `engine/scripts/terrain/TerrainWorld.gd:322` binds only first
     slot's sibling array
   - Severity: critical (user-visible bug; texture team's mid + rock
     work is dead weight in renderer)

3. **Sibling 3-tap noise frequency too low → visible repeat at
   standing-eye height**
   - Spec: 24_GROUND_VARIETY Quality bar "no obvious texture repeats"
   - Code: `engine/shaders/terrain_clipmap.gdshader` defaults
     `sibling_blend_freq = 0.10` (10m wavelength) on 4m tiles —
     same tile appears 2-3 times in a row at standing height
   - Severity: significant (visible at close-mid range; not as bad
     as A+B above)

Additional findings the subagents are expected to find:

4. Macro albedo (Layer 3) not authored in walking demo → far-field
   falls back to fallback_color (spec 23 + 24)
5. Detail overlays (Layer 2) not authored → spec 24 trifecta only
   has Layer 1 active
6. ErosionKernel not built → terrain heightfield is fBm-only;
   no valleys, no ridges, no drainage (spec 19)
7. DemFeatureKernel not built → no real-world terrain anchoring
   (spec 19)
8. Phase 4 build-notes don't acknowledge any of #1-#3 → audit trail
   missed the gaps

## Out of scope

- Phase 6+ work that hasn't been started (decoration, foliage, etc.)
- Performance regressions (the calibration sprint already
  audited those)
- Documentation polish (handled by spec status sweep at Phase 5 close)

## How findings translate to action

After the punch-list lands:

1. Critical findings get their own sub-phases (4.9.a, 4.9.b, ...)
   with plan docs + TDD before code
2. Significant findings get bundled into the next natural sprint
   (e.g. fold sibling-noise tuning into Phase 5.6 calibration)
3. Minor findings get a `docs/strategy/PHASE_DEBT.md` to track for
   later sweep
4. ROADMAP.md gets explicitly amended to reflect what each phase
   actually delivered (vs claimed) so the sync doesn't drift again
